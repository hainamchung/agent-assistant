## Request Lifecycle

The complete path of a user request from input to deliverable:

```
User Input
    │
    ▼
┌─────────────────┐
│ Platform Entry   │  (e.g., COPILOT.md)
│ File Loaded      │  → triggers boot sequence
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ RUNTIME.md      │  Tiered loading (NANO/MICRO/FULL)
│ Loaded           │  → Orchestrator identity activated
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Command          │  Explicit /command OR natural language mapping
│ Detection        │  → determines command + variant
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Workflow         │  commands/{cmd}/{variant}.md loaded
│ Loading          │  → phase list with agent assignments
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Phase Loop       │  For each phase in workflow:
│                  │  1. Detect execution mode (EMBODY/SUB-AGENT)
│                  │  2. Load agent definition
│                  │  3. Resolve skills (HSOL)
│                  │  4. Apply guardrails
│                  │  5. Execute agent protocol
│                  │  6. Verify exit criteria
│                  │  7. Checkpoint (if durable)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Evaluation       │  5-dimension scoring (D1-D5)
│                  │  D4 Security override check
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Deliverable      │  Synthesized output to user
│ Output           │  (code, docs, plan, review, etc.)
└─────────────────┘
```

## Boot Sequence Flow

The document-driven boot sequence that activates the orchestrator:

```
1. AI tool opens project
2. Platform entry file detected:
   ~/.<platform>/skills/agent-assistant/<PLATFORM>.md
3. Entry file contains: boot instruction to read RUNTIME.md
4. RUNTIME.md §LOADING PROTOCOL evaluated:
   - Simple task → load §NANO only (~500 words)
   - Standard task → load §NANO + §MICRO (~1500 words)
   - Complex task → load full RUNTIME.md (~3200 words)
5. Orchestrator identity activated — all Laws internalized
6. Waiting for user input
```

**Key Insight**: There is no server startup, no process launch. The "boot" is the AI model reading configuration documents that shape its behavior.

## Command Execution Flow

```
User: "/cook:fast add health check endpoint"
  │
  ├─ Step 1: Detect command = "cook", variant = "fast"
  │
  ├─ Step 2: Load commands/cook.md (router)
  │           Router confirms variant → load commands/cook/fast.md
  │
  ├─ Step 3: Parse workflow phases from fast.md:
  │           Phase 1: Scouter → reconnaissance
  │           Phase 2: Backend-engineer → implementation
  │           Phase 3: Tester → verification (optional in :fast)
  │
  ├─ Step 4: Execute Phase 1 (EMBODY scouter)
  │           - Read agent file, extract protocol
  │           - Scan project structure
  │           - Emit reconnaissance deliverable
  │           - Verify exit criteria
  │
  ├─ Step 5: Execute Phase 2 (EMBODY backend-engineer)
  │           - Load agent file
  │           - HSOL resolves skills for profile "backend:execution"
  │           - Apply guardrails [injection-defense, output-sanitization, io-pipeline]
  │           - Implement the health check endpoint
  │           - Emit code deliverable
  │
  └─ Step 6: Deliver result to user
```

## Agent Delegation Flow

Two execution modes determine how agents are activated:

### EMBODY Mode (meta, execution, investigation, support)
```
Orchestrator
  │
  ├─ READ agents/{agent}.md completely
  ├─ EXTRACT directive, protocol, constraints
  ├─ ANNOUNCE "📋 EMBODIED: {agent}"
  ├─ EXECUTE as that agent (within orchestrator context)
  ├─ GENERATE deliverable
  └─ EXIT → return to orchestrator identity
```
**Context**: Shared with orchestrator — continuity preserved.

### SUB-AGENT Mode (validation, research)
```
Orchestrator
  │
  ├─ PREPARE context briefing:
  │   - Objective
  │   - Scope boundaries
  │   - Facts (no opinions)
  │   - Constraints
  │
  ├─ INVOKE runSubagent(agent_name, context)
  │   └─ Agent executes in isolated context
  │   └─ Returns deliverable
  │
  ├─ VERIFY output meets exit criteria
  └─ On failure: retry with feedback OR fallback to EMBODY + Anti-Bias Protocol
```
**Context**: Isolated — prevents bias contamination from prior phases.

## Skill Resolution Flow

```
Agent activated with profile "backend:execution"
  │
  ├─ Step 1: Parse profile → domain="backend", category="execution"
  │
  ├─ Step 2: Load matrix-skills/backend.yaml
  │           Match profile against registry entries
  │           → Resolve matching skills
  │
  ├─ Step 3: Detect project context signals
  │           (e.g., Express.js found → Node.js backend skills)
  │
  ├─ Step 4: Merge matrix skills + library skills
  │           skills/*/SKILL.md for deep expertise
  │
  ├─ Step 5: Apply skill-profile filter
  │           Agent's skill-profile="REST API" → prioritize REST skills
  │
  └─ Step 6: Inject resolved skills into agent context
```

## Guardrail Pipeline Flow

From `guardrails/io-pipeline.md` — 4-stage processing:

```
Agent receives task
  │
  ├─ Stage 1: VALIDATE
  │   - Input sanitization
  │   - Injection detection (guardrails/injection-defense.md)
  │   - Scope verification (agent's scope.files, scope.tasks)
  │   - If violation → ESCALATE immediately
  │
  ├─ Stage 2: PROCESS
  │   - Core task execution
  │   - Agent applies its operational protocol
  │   - Guardrails monitor for constraint violations
  │
  ├─ Stage 3: FORMAT
  │   - Output sanitization (guardrails/output-sanitization.md)
  │   - PII/sensitive data check (guardrails/data-privacy.md)
  │   - Style and voice coherence check
  │
  └─ Stage 4: ESCALATE (if needed)
      - Violation classification (guardrails/violation-escalation.md)
      - Severity assessment
      - Notify user with options
      - Log violation details
```

## Team Execution Flow

Golden Triangle team execution (`:team` variant):

```
/cook:team "implement authentication"
  │
  ├─ Step 1: Resolve team for domain (backend-team)
  │           Tech Lead: tech-lead
  │           Executor: backend-engineer
  │           Reviewer: reviewer
  │
  ├─ Step 2: Tech Lead decomposes task
  │           - Break into sub-tasks
  │           - Define acceptance criteria
  │           - Set scope boundaries
  │
  ├─ Step 3: Executor implements
  │           - Follow Tech Lead's decomposition
  │           - Apply HSOL-resolved skills
  │           - Emit code deliverable
  │
  ├─ Step 4: Reviewer adversarially challenges
  │           - Independent context (SUB-AGENT mode)
  │           - Apply EVALUATION.md 5-dimension scoring
  │           - Flag issues, suggest improvements
  │
  ├─ Step 5: Iteration (if needed)
  │           - Executor addresses reviewer findings
  │           - Reviewer re-evaluates
  │           - Maximum 2 rounds before Tech Lead decides
  │
  └─ Step 6: Tech Lead synthesizes final deliverable
```

## Checkpoint-Resume Flow

From `rules/DURABLE-EXECUTION.md`:

```
Phase N executing
  │
  ├─ Phase completes → checkpoint saved
  │   - Phase number, agent, deliverable reference
  │   - TTL: 24 hours
  │
  ├─ [Interruption occurs]
  │
  ├─ User re-engages
  │   - Orchestrator detects existing checkpoint
  │   - Loads checkpoint state
  │   - Resumes from Phase N+1
  │
  └─ If TTL expired → restart from Phase 1
```

## CLI Installation Flow

```
npm install -g @namch/agent-assistant
  │
  ├─ Global package installed to npm global prefix
  │
agent-assistant install copilot
  │
  ├─ Step 1: Detect target platform → "copilot"
  ├─ Step 2: Resolve platform config from platforms.json
  ├─ Step 3: Determine install path → ~/.copilot/
  ├─ Step 4: Generate entry file from AGENT.template.md
  │           - Inject platform-specific capability block
  │           - Inject platform overrides
  ├─ Step 5: Sync framework files to:
  │           ~/.copilot/skills/agent-assistant/
  │           ├── agents/
  │           ├── commands/
  │           ├── rules/
  │           ├── skills/ (selected)
  │           ├── matrix-skills/
  │           ├── topologies/
  │           ├── guardrails/
  │           ├── personas/
  │           └── schemas/
  ├─ Step 6: Verify file integrity
  └─ Step 7: Report success with file counts
```

## Document-Driven Architecture

**Problem**: Traditional multi-agent systems require custom runtime engines, message buses, and coordination services.

**Solution**: Use Markdown and YAML files as the execution medium. The AI model itself is the runtime — it reads documents and follows them as instructions. No separate server, message bus, or coordination service is needed.

**Implementation**:
- Agents are `.md` files with YAML frontmatter → loaded into AI context
- Commands are `.md` files defining workflows → parsed as phase instructions
- Rules are `.md` files defining protocols → internalized as behavioral constraints
- Skills are YAML registries → resolved at task start

**Trade-offs**:
- (+) Zero infrastructure overhead — works in any AI tool's context window
- (+) Human-readable and editable — contributors modify Markdown, not code
- (-) No runtime state beyond the AI model's conversation context
- (-) Dependent on AI model's instruction-following capability

## Orchestrator Pattern

**Problem**: Without a central coordinator, agents would conflict, skip steps, or implement directly instead of collaborating.

**Solution**: A single Orchestrator identity defined in `RUNTIME.md` that never implements — it only delegates, coordinates, and verifies.

**Implementation**:
- Orchestrator Laws enforced: "You are the ORCHESTRATOR — NOT an IMPLEMENTER"
- Prohibitions table: cannot write code, debug, test, or make architecture decisions
- Self-check protocol runs before every response
- Phase ordering is strict — cannot skip or reorder

**Classic GoF Parallel**: Mediator pattern — the Orchestrator mediates all agent interactions.

## Command-Router Pattern

**Problem**: Users need flexible entry points — sometimes quick, sometimes thorough, sometimes adversarial — for the same task type.

**Solution**: Two-level routing: a router file dispatches to variant workflow files based on execution mode.

**Implementation**:
```
commands/cook.md          ← Router: detects :fast/:hard/:team suffix
commands/cook/fast.md     ← Fast variant workflow
commands/cook/hard.md     ← Default (thorough) variant
commands/cook/team.md     ← Team (Golden Triangle) variant
```

**Classic Parallel**: Strategy pattern — the variant is the strategy, the router is the context.

## Agent-As-Persona Pattern

**Problem**: A single AI model playing multiple roles risks blending behaviors, losing expertise boundaries, and self-reviewing its own work.

**Solution**: Define each agent as a distinct persona with explicit role, scope, capabilities, restrictions, and handoff protocols.

**Implementation** (from agent frontmatter):
- `role-scope`: restricts to implementation/coordination/analysis/review/research/support
- `scope.files`: glob patterns limiting file access
- `scope.restrictions`: explicit forbidden actions (e.g., `no-frontend-changes`)
- `guardrails`: applied safety constraints
- `preflight`: pre-execution checks that must pass

**Execution Modes**:
- EMBODY: Orchestrator temporarily assumes the persona (shared context)
- SUB-AGENT: Agent runs in isolated context (bias prevention for reviewers)

## Strategy Pattern via Topologies

**Problem**: Different tasks require different multi-agent coordination patterns.

**Solution**: 12 topology templates define coordination strategies. The workflow selects the appropriate topology.

**Implementation**: Each topology file in `topologies/` defines:
- Agent roles and ordering
- Parallelism rules
- Synthesis/merge logic
- Exit criteria

**Classic Parallel**: Strategy pattern — topologies are interchangeable coordination strategies.

## Layered Guardrail Pipeline

**Problem**: Agents operating without constraints could produce unsafe, biased, or policy-violating output.

**Solution**: A 4-stage pipeline (Validate → Process → Format → Escalate) with 7 guardrail modules applied per agent.

**Implementation**: Agents declare guardrails in frontmatter. The I/O pipeline processes every agent action through:
1. Input validation and injection defense
2. Core task processing with monitoring
3. Output sanitization and privacy checks
4. Violation escalation protocol

**Classic Parallel**: Chain of Responsibility / Middleware pipeline.

## Tiered Loading Pattern

**Problem**: Loading the full 3200-word RUNTIME.md for every task wastes context window budget on simple tasks.

**Solution**: Three loading tiers that progressively expand the loaded protocol:

| Tier | Size | Content |
|------|------|---------|
| NANO | ~500w | Identity, laws, basic routing |
| MICRO | ~1500w | + execution model, delegation rules |
| FULL | ~3200w | + all rules, team protocols, error handling |

**Implementation**: `RUNTIME.md` §LOADING PROTOCOL evaluates task complexity and loads only the necessary tier. Reduces context usage by up to 85% for simple tasks.

**Classic Parallel**: Lazy loading / Progressive enhancement.

## Golden Triangle (Adversarial Collaboration)

**Problem**: Self-review by the implementing agent provides no meaningful quality challenge.

**Solution**: Three-agent adversarial teams where implementation and review are performed by different agents with independent context.

**Implementation**:
- 17 domain-specific teams in `agents/teams/`
- Each team: Tech Lead (decomposition) + Executor (implementation) + Reviewer (adversarial challenge)
- Reviewer runs in SUB-AGENT mode (isolated context) to prevent bias from seeing the implementation process
- Maximum 2 iteration rounds before Tech Lead decides

**Classic Parallel**: Adversarial collaboration / Red team pattern.

## Hybrid Skill Resolution

**Problem**: Manually wiring domain skills to agents doesn't scale across 1400+ skills and 21 agents.

**Solution**: Three-tier automatic resolution based on agent profile matching.

**Implementation**:
1. Matrix Skills — YAML registries with profile→skill mappings
2. Library Skills — Deep skill directories resolved by profile + project signals
3. Dynamic Skills — Community extensions via `_dynamic.yaml`

**Classic Parallel**: Service Locator / Dependency Injection (runtime resolution based on profile metadata).

## Template-Driven Generation

**Problem**: Supporting 6 platforms requires 6 entry files that must stay in sync with the framework.

**Solution**: Generate platform entry files from a single template + platform configuration.

**Implementation**:
- `AGENT.template.md` — Template with `{{CAPABILITIES_BLOCK}}` and `{{OVERRIDES_BLOCK}}` placeholders
- `platforms.json` — Platform-specific values
- `scripts/generate-entry-points.js` — Generator script
- `scripts/lint-entry-points.js` — Drift detection (CI-enforced)

**Classic Parallel**: Template Method pattern / Code generation.

---

## Zero-Dependency CLI

**Problem**: External dependencies introduce supply chain risk, increase install size, and add maintenance burden.

**Solution**: Build the entire CLI using only Node.js built-in modules.

**Implementation**:
- `cli/` uses only `fs`, `path`, `readline`, `crypto`, `child_process`
- Custom `yaml-lite.js` parser instead of a YAML library
- `dependencies: {}` in `package.json` (empty)
- Only dev dependencies for release tooling

**Classic Parallel**: Self-contained module / Minimal dependency principle.

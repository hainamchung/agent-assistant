## ADR-001: Document-Driven Architecture

**Status**: Accepted (v1.0)

**Context**: Building a multi-agent orchestration system that works across 6 different AI coding platforms, each with different APIs, context windows, and capabilities.

**Decision**: Use Markdown and YAML files as the execution medium. The AI model reads and follows documents as instructions, rather than calling APIs or running code.

**Rationale**:
- All AI coding tools can read Markdown files from the filesystem
- No runtime infrastructure needed — no servers, databases, or message buses
- Human-readable: contributors can edit agents and commands by editing text
- Platform-agnostic: the same files work across all 6 platforms

**Trade-offs**:
- (+) Zero infrastructure cost, instant portability
- (+) Version-controlled via git — full audit trail
- (-) No persistent state beyond conversation context
- (-) Performance depends on AI model's instruction-following quality

**Alternatives Considered**:
- Custom runtime engine with agent APIs → Too complex, platform-specific
- Plugin systems per AI tool → Fragmented, non-portable
- MCP server approach → Added as supplement (`scripts/mcp-server.js`), not primary

## ADR-002: Global Install Model

**Status**: Accepted (v1.0)

**Context**: Users work across many projects and shouldn't need to set up the framework per-project.

**Decision**: Install globally to `~/.<platform>/` so every project opened in that AI tool gets the framework automatically.

**Rationale**:
- Install once, available everywhere — reduces ceremony per repo
- AI tools scan their respective home directories for configuration
- Update globally with one command (`npm install -g @namch/agent-assistant@latest`)

**Trade-offs**:
- (+) Zero per-project setup
- (+) Consistent experience across all projects
- (-) All projects share the same framework version (no per-project pinning)
- (-) Requires filesystem write access to home directory

## ADR-003: Zero External Dependencies for CLI

**Status**: Accepted (v1.0)

**Context**: The CLI is globally installed by users who trust it with filesystem access.

**Decision**: Use only Node.js built-in modules for the CLI. Zero entries in `dependencies`.

**Rationale**:
- Eliminates supply chain attack surface
- Reduces install size (no `node_modules` bloat)
- Faster install, no resolution or lockfile issues
- Node.js built-ins (`fs`, `path`, `readline`, `crypto`) cover all needs

**Trade-offs**:
- (+) Zero supply chain risk
- (+) Minimal install footprint
- (-) Custom YAML parser needed (`yaml-lite.js`) instead of using established library
- (-) More verbose code for some operations (e.g., interactive prompts)

## ADR-004: Markdown as Agent Definition Format

**Status**: Accepted (v1.0)

**Context**: Agent definitions need to be both machine-parseable and human-readable.

**Decision**: Define agents as Markdown files with YAML frontmatter for structured metadata and Markdown body for behavioral instructions.

**Rationale**:
- YAML frontmatter provides structured fields (name, profile, handoffs, guardrails)
- Markdown body provides rich behavioral instructions with formatting
- Both parts are natively readable by AI models
- Easy to validate with scripts (`lint-agents.js`)

**Trade-offs**:
- (+) Human-readable and editable
- (+) AI models process Markdown natively
- (+) Scriptable validation via frontmatter parsing
- (-) Schema enforcement requires custom tooling (not JSON Schema)
- (-) Complex structured data is awkward in YAML frontmatter

## ADR-005: Tiered Context Loading

**Status**: Accepted (v2.0)

**Context**: The full RUNTIME.md is ~3200 words. Loading it for every task wastes context budget, especially for simple operations.

**Decision**: Split RUNTIME.md into three loading tiers: NANO (~500w), MICRO (~1500w), FULL (~3200w). Load only what the task requires.

**Rationale**:
- Simple tasks (one-file edit) save ~85% context budget
- Token savings compound across multi-phase workflows
- Same protocol, different granularity — no parallel maintenance

**Trade-offs**:
- (+) Up to 85% context savings for simple tasks
- (+) More context available for actual work
- (-) Tier detection adds complexity to boot sequence
- (-) Underfitting (loading NANO for a complex task) risks protocol violations

## ADR-006: Dual Execution Modes (EMBODY vs SUB-AGENT)

**Status**: Accepted (v2.0)

**Context**: Some agents need shared context with the orchestrator (e.g., tech-lead coordinating phases) while others need isolation (e.g., reviewer independently evaluating code).

**Decision**: Use two execution modes based on agent category:
- EMBODY: Orchestrator assumes agent persona (shared context) — for meta, execution, investigation, support agents
- SUB-AGENT: Agent runs in isolated context — for validation and research agents

**Rationale**:
- Reviewers in SUB-AGENT mode don't see how code was produced → reduces confirmation bias
- Execution agents in EMBODY mode maintain conversation continuity
- Category-based rule is simple and predictable

**Trade-offs**:
- (+) Bias prevention for evaluators
- (+) Context continuity for implementers
- (-) SUB-AGENT requires `runSubagent` tool (not available on all platforms)
- (-) Fallback to EMBODY + Anti-Bias Protocol is a weaker guarantee

## ADR-007: Adversarial Golden Triangle Teams

**Status**: Accepted (v2.0)

**Context**: Code generated and reviewed by the same AI agent is essentially self-review, providing no meaningful quality challenge.

**Decision**: Implement 17 domain-specific teams with Tech Lead + Executor + Reviewer in an adversarial collaboration pattern.

**Rationale**:
- Reviewer operates in isolated context → genuine independent evaluation
- Tech Lead provides decomposition expertise → better task structure
- Bounded iteration (max 2 rounds) → prevents infinite loops
- Domain-specific teams → right expertise for each task type

**Trade-offs**:
- (+) Genuine adversarial review
- (+) Better task decomposition
- (-) 3x token cost vs single-agent execution
- (-) Slower than single-agent for simple tasks

## ADR-008: YAML Frontmatter for Agent Schema

**Status**: Accepted (v1.0)

**Context**: Need a structured schema for agent metadata that coexists with Markdown body content.

**Decision**: Use YAML frontmatter (delimited by `---`) with a defined schema (v1.0) validated by `lint-agents.js`.

**Rationale**:
- Standard Markdown convention (used by Jekyll, Hugo, Docusaurus)
- Parseable by both custom scripts and AI models
- Coexists naturally with Markdown content
- Schema v1.0 defines 15+ fields with validation rules R001-R302

**Trade-offs**:
- (+) Industry-standard format
- (+) Custom YAML-lite parser avoids external deps
- (-) Complex nested structures push YAML readability limits
- (-) No formal JSON Schema — validation is custom scripted

## ADR-009: Six-Platform Parity via Template Generation

**Status**: Accepted (v2.0)

**Context**: Supporting 6 platforms requires keeping 6 entry files in sync with capability differences.

**Decision**: Use a single template (`AGENT.template.md`) + platform config (`platforms.json`) + generator script (`generate-entry-points.js`) to produce all entry files. Enforce drift detection in CI.

**Rationale**:
- Single source of truth — change template, regenerate all
- Platform differences captured in `platforms.json` as data, not code duplication
- CI drift detection (`lint-entry-points.js`) prevents committed files from diverging

**Trade-offs**:
- (+) Single source of truth
- (+) Adding a new platform = adding a JSON entry
- (-) Template syntax complexity (mustache-like placeholders)
- (-) Generator script maintenance

## ADR-010: Conventional Commits with Semantic Release

**Status**: Accepted (v1.0)

**Context**: Need automated versioning and changelog generation for npm publishing.

**Decision**: Enforce conventional commits via Husky commit-msg hook, use semantic-release for automated versioning, changelog, and npm publishing.

**Rationale**:
- Consistent commit history with machine-readable types
- Automated version bumps based on commit semantics
- Generated CHANGELOG.md with categorized entries
- No manual version management

**Trade-offs**:
- (+) Fully automated release pipeline
- (+) Consistent changelog format
- (-) Contributors must learn conventional commit format
- (-) Depends on 5 dev dependencies (semantic-release plugins)
